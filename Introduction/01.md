# study about the status code mdn

HTTP response status codes indicate whether a specific HTTP request has been successfully completed. Responses are grouped in five classes:

    1.Informational responses (100 - 199)
    2.Successful responses (200 - 299)
    3.Redirection messages (300 -  399)
    4.Client error responses (400 -  499)
    5.Server error responses (500 -  599)

# HTTP HEAD and OPTIONS Requests

Apart from GET, POST, PUT, PATCH, and DELETE, HTTP also provides methods such as **HEAD** and **OPTIONS**.

---

# 1. HEAD Request

## What is HEAD?

**HEAD** is an HTTP request method that works similarly to **GET**, but the server **does not send the response body**.

In simple words:

> **HEAD means: "Give me the information about this resource, but don't send me the actual content."**

---

## Purpose of HEAD

HEAD is mainly used when the client wants to check information about a resource **without downloading the resource itself**.

For example, a client may want to know:

* Whether a resource exists
* The size of a file
* The type of content
* When the resource was last modified
* Other response headers

Example:

```http
HEAD /images/photo.jpg
```

The server can respond with headers such as:

```http
HTTP/1.1 200 OK
Content-Type: image/jpeg
Content-Length: 245000
Last-Modified: ...
```

But it does **not** send the actual image in the response body.

---

# 2. HEAD vs GET

HEAD and GET are closely related.

### GET

```http
GET /photo.jpg
```

The server returns:

```text
Headers
+
Actual photo
```

### HEAD

```http
HEAD /photo.jpg
```

The server returns:

```text
Headers
+
No response body
```

So:

```text
GET
 ↓
"Give me the resource."

HEAD
 ↓
"Give me the information about the resource,
 but not the resource itself."
```

---

# 3. Why Use HEAD?

Imagine you have a very large file:

```text
video.mp4 → 2 GB
```

Before downloading it, a client might want to check:

```text
Does the file exist?
What is its size?
What type of file is it?
When was it modified?
```

Instead of downloading the entire 2 GB file, it can send:

```http
HEAD /video.mp4
```

The server can return the relevant headers without sending the video.

This can save bandwidth and time.

---

# 4. Is HEAD Idempotent?

**Yes, HEAD is idempotent.**

HEAD does not normally modify the resource.

Sending:

```http
HEAD /users/1
```

once or multiple times does not change the user's data.

```text
HEAD × 1
HEAD × 10
HEAD × 100

      ↓

Same intended server state
      ↓
   Idempotent
```

HEAD is also considered **safe**, because it is intended only to retrieve information.

---

# 5. OPTIONS Request

## What is OPTIONS?

**OPTIONS** is an HTTP request method used to ask a server **what communication options are available for a particular resource or endpoint**.

In simple words:

> **OPTIONS means: "What can I do with this resource?"**

For example:

```http
OPTIONS /users
```

The server might respond with:

```http
Allow: GET, POST, PUT, DELETE, OPTIONS
```

This tells the client which HTTP methods are allowed for that endpoint.

---

# 6. Purpose of OPTIONS

OPTIONS can be used to:

* Discover which HTTP methods are supported
* Discover communication options for a resource
* Handle **CORS** preflight requests in web applications

For example:

```http
OPTIONS /users
```

The server may respond:

```http
Allow: GET, POST, PUT, DELETE, OPTIONS
```

The client now knows which methods are supported.

---

# 7. OPTIONS and CORS

One of the most important real-world uses of OPTIONS is **CORS (Cross-Origin Resource Sharing)**.

Suppose your frontend is running at:

```text
http://localhost:5173
```

and your backend is running at:

```text
http://localhost:3000
```

These are different origins.

Before sending certain cross-origin requests, the browser may first send an **OPTIONS request** to the server.

This is called a **CORS preflight request**.

Conceptually:

```text
Browser
   |
   | OPTIONS
   | "Is this cross-origin request allowed?"
   ↓
Backend
   |
   | Response with CORS permissions
   ↓
Browser
   |
   | Actual request
   ↓
Backend
```

For example, the browser might ask:

```http
OPTIONS /users
Origin: http://localhost:5173
Access-Control-Request-Method: POST
```

The server can respond with appropriate CORS headers indicating whether that request is permitted.

---

# 8. Is OPTIONS Idempotent?

**Yes, OPTIONS is idempotent.**

It is intended to ask about the available communication options and does not normally modify the resource.

Therefore, sending:

```http
OPTIONS /users
```

multiple times does not normally change the resource.

```text
OPTIONS × 1
OPTIONS × 10
OPTIONS × 100

       ↓

No intended change to the resource
       ↓
    Idempotent
```

OPTIONS is also considered **safe**.

---

# 9. HEAD vs OPTIONS

These two methods can be confusing because both don't normally retrieve the actual resource.

The key difference is **what you're asking the server**.

### HEAD

> **"Tell me about this resource, but don't send its content."**

Example:

```http
HEAD /photo.jpg
```

You may get:

```text
Content-Type
Content-Length
Last-Modified
```

---

### OPTIONS

> **"Tell me what operations/communication options are available for this resource."**

Example:

```http
OPTIONS /users
```

You may get:

```text
Allow: GET, POST, PUT, DELETE
```
